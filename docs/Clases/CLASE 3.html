Fase 1 · Teoría · Paso 02

Validación de entradas: "toda entrada es hostil"

La validación de entradas es la primera línea de defensa de cualquier herramienta. OWASP ASVS la trata como el control más crítico: la mayoría de vulnerabilidades graves (inyección SQL, XSS, command injection, path traversal) nacen de no validar correctamente lo que entra al sistema.

Por qué la validación del cliente no sirve

Un error común de los equipos noveles es confiar en la validación del navegador o de la interfaz. Un atacante puede saltarse el navegador con un proxy (Burp Suite, OWASP ZAP) o con curl y enviar peticiones directamente al servidor. La validación real ocurre en el servidor, en cada punto de entrada: formularios, APIs, cabeceras HTTP, cookies, archivos, parámetros de URL.

Error clásico "Validé el campo en JavaScript, así que el servidor está protegido." Falso. El atacante no usa tu JavaScript. Envía la petición directamente y el servidor recibe lo que él quiere.

Validación positiva (lista blanca) vs. negativa (lista negra)

ASVS exige validación positiva: definir exactamente qué se permite y rechazar todo lo demás. La validación negativa ("bloquear caracteres raros") falla porque siempre hay una codificación o sintaxis que el atacante puede usar para evadir el filtro.

TipoEnfoqueProblema
Lista blanca (positiva)Definir qué es válido: "solo IPv4 en formato X.Y.Z.W, puerto entre 1 y 65535"Ninguno. Es el enfoque correcto.
Lista negra (negativa)Bloquear caracteres conocidos como peligrosos: ;, |, <, >El atacante usa codificación Unicode, saltos de línea, o sintaxis alternativa que el filtro no contempla.

Validación aplicada a una herramienta de red

Si su herramienta recibe una IP o un puerto para escanear, no basta con "limpiar" la entrada. Deben validar:

  • IP: que sea una IPv4 o IPv6 válida (usar una librería de parsing, no una regex frágil).
  • Puerto: que sea un número entero entre 1 y 65535.
  • Comando: que no incluya caracteres de shell (;, |, &, backticks) si van a ejecutar comandos del sistema.
  • Longitud: rechazar entradas que excedan un tamaño razonable (previene buffer overflows y DoS).
Cita normativa OWASP ASVS 5.0, sección V5 (Validación de Entradas). Requisitos nivel 1: 5.3 (fallos de validación se rechazan y se registran) y 5.5 (validación aplicada en el servidor). NIST SSDF PW.7 (revisar código para identificar vulnerabilidades antes del release).

Fase 1 · Teoría · Paso 03

Manejo de errores y logging: "no alimentes al atacante"

Los errores son información. Si su herramienta muestra un stack trace con rutas del servidor, versiones de librerías o consultas SQL, le están dando al atacante un mapa de su infraestructura. ASVS exige que el usuario vea un mensaje genérico y que el detalle vaya solo al log interno.

La regla del mensaje genérico

Cuando algo falla, el usuario debe ver algo como: "Ocurrió un error. Contacte al administrador." El detalle técnico (línea de código, mensaje de la base de datos, ruta del archivo) se escribe en el log interno, que solo el equipo puede leer. Esto previene information disclosure (fuga de información), una de las amenazas STRIDE que modelaron en la Clase 1.

Lo que el usuario veLo que va al log internoPor qué
"Error al procesar la solicitud."Error en línea 45 de parser.py: índice fuera de rango en array de puertos.El usuario no necesita saber dónde falló el código. El atacante tampoco.
"Credenciales inválidas."Intento de login fallido para usuario admin desde IP 192.168.1.50 a las 14:32:05.No se revela si el usuario existe o no (evita enumeración de usuarios).

Logging de auditoría: qué registrar y qué NO

No se trata de registrar todo. Se trata de registrar lo relevante para seguridad: intentos de autenticación fallidos, accesos denegados, cambios de configuración, errores de validación de entradas, acciones administrativas. El log debe responder: ¿quién?, ¿qué?, ¿cuándo?, ¿desde dónde?

Lo que NUNCA debe ir al log Contraseñas en texto plano. Tokens de sesión sin hashear. Datos personales sensibles (cédulas, correos completos). Claves de API. Si necesitan correlacionar una sesión, hasheen el token antes de escribirlo.
Cita normativa OWASP ASVS 5.0, V7 (Manejo de Errores y Logging). Requisito 7.4.1: mensaje genérico al usuario. Requisito 7.1.1: no loguear credenciales. NIST SSDF PW.9 (configuraciones seguras por defecto, incluyendo logging).

Fase 1 · Teoría · Paso 04

Cifrado: "no inventes tu propia criptografía"

Hay dos momentos críticos: datos en tránsito y datos en reposo. En ambos, la regla es la misma: usar algoritmos estándar, nunca caseros, nunca obsoletos.

En tránsito (TLS)

Toda comunicación entre componentes de su herramienta (consola ↔ agentes, API ↔ cliente) debe ir por TLS 1.2 o superior. TLS 1.0 y 1.1 están deprecados desde 2021. Nunca desactiven la validación de certificados con verify=False o equivalentes: eso anula toda la protección contra ataques de intermediario (MITM).

Error clásico en Python requests.get(url, verify=False) desactiva la validación del certificado. El equipo cree que "funciona" porque no lanza error, pero en realidad están aceptando cualquier certificado, incluido el de un atacante.

En reposo (contraseñas y datos sensibles)

Si su herramienta almacena credenciales de usuarios, jamás las guarden en texto plano ni con MD5/SHA-1. MD5 puede calcular ~10 mil millones de hashes por segundo en una GPU moderna; una contraseña de 6 caracteres cae en menos de un segundo. Usen Argon2 (recomendación actual de OWASP), bcrypt (con factor de costo 12) o PBKDF2 (con al menos 600,000 iteraciones). Estas funciones son lentas a propósito y generan salt automático.

AlgoritmoEstadoRecomendación
MD5RotoNunca usar para contraseñas.
SHA-1DeprecadoNunca usar para contraseñas.
SHA-256 (simple)RápidoNo usar para contraseñas: demasiado rápido, vulnerable a fuerza bruta.
bcrypt / Argon2 / PBKDF2RecomendadoUsar con factor de costo o iteraciones adecuadas.
Cita normativa OWASP ASVS 5.0, V6 (Criptografía) y V9 (Comunicaciones). Nivel 1: TLS moderno y hashing de contraseñas con algoritmos lentos. NIST SSDF PW.9 (configuraciones seguras).

Fase 1 · Teoría · Paso 05

SAST y secretos: tu código también se audita

El análisis estático (SAST) examina el código sin ejecutarlo, buscando patrones peligrosos: inyecciones, uso de funciones inseguras, flujos de datos desde fuentes no confiables hacia sinks peligrosos. No es una bala de plata, pero es mejor que no revisar nada.

Cómo interpretar un reporte SAST

No se asusten por el número de hallazgos. Prioricen por:

  1. ¿El dato viene realmente de un usuario no confiable? Si el hallazgo está en una función interna que solo recibe datos validados, probablemente es falso positivo.
  2. ¿Hay una sanitización en el camino que la herramienta no reconoció? SAST a veces no ve que ya validaron la entrada antes de pasarla al sink.
  3. ¿El sink realmente interpreta el dato de forma peligrosa? No es lo mismo concatenar una cadena para mostrarla que pasarla a eval() o a una consulta SQL.

Un hallazgo de severidad alta pero confianza baja es una pregunta, no una emergencia. Un hallazgo de severidad baja pero confianza alta en un punto de entrada crítico es prioritario.

Secretos en el repositorio: el error catastrófico

Un error clásico y devastador: subir al repositorio un archivo .env con la API key de un servicio, la contraseña de la base de datos, o el token de un agente de IA. Cualquiera con acceso al repo (o un atacante que lo comprometa) tiene acceso a todo.

Regla de oro Los secretos nunca van en el código. Van en variables de entorno o en un gestor de secretos. Antes de cada commit, revisen que no haya quedado nada sensible. Si ya subieron un secreto, no basta con borrarlo del archivo: hay que revocar la clave y asumir que fue comprometida.
Cita normativa NIST SSDF PW.7 (revisar código para identificar vulnerabilidades antes del release) y PS.1 (proteger toda la información del repositorio, incluidos los secretos).
